# Pruebas de carga con k6

Herramienta nueva del TP de Calidad de Software: pruebas de carga sobre **staging**, nunca sobre producción. Este documento sigue el proceso de cinco pasos (requisitos, mercado, prueba de concepto, matriz de decisión y despliegue incremental) y deja los comandos para correrlas.

| Pieza | Dónde |
|---|---|
| Configuración común y lecturas | `scripts/carga/comun.js` |
| Guardas (staging confirmado, nunca producción) | `scripts/carga/guardas.mjs`, tests en `scripts/carga/guardas.test.mjs` |
| Escenarios | `scripts/carga/humo.js`, `scripts/carga/stress.js`, `scripts/carga/soak.js` |
| Workflow | `.github/workflows/carga-k6.yml` (solo `workflow_dispatch`) |

Los resultados de staging todavía no existen: todo lo que dependa de una corrida está marcado `[PENDIENTE: corrida del dd/mm]`.

## 1. Requisitos

Lo que tiene que cumplir la herramienta y la forma de usarla en MenYU:

1. **Nunca cargar producción.** El script corta antes de la primera request si falta `CONFIRMAR_STAGING=si` o si el host es de producción (sección 6).
2. **Solo lecturas en la primera etapa.** `GET /health` y las lecturas públicas de Discovery y del menú, que no escriben en la base (`apps/backend/src/discovery/discovery.controller.ts`, `apps/backend/src/menu/menu.controller.ts`). Un flujo que escriba queda como propuesta aparte (sección 5.4).
3. **Umbrales automáticos.** Tasa de error (`http_req_failed`) y p95 de `http_req_duration`. La prueba falla sola si no se cumplen.
4. **Resultado como archivo.** Un resumen JSON que el workflow sube como artifact.
5. **Versionado y reproducible.** Scripts en el repo, versión de la herramienta fijada y corrida desde GitHub Actions, como el resto del pipeline.
6. **Mantenible por el equipo.** El equipo escribe TypeScript y JavaScript (`CLAUDE.md`, "Stack"): conviene que los scripts sean JavaScript.
7. **Sin costo.** Una herramienta de código abierto que corra en el runner de GitHub, sin servicio pago.

## 2. Mercado

Las cuatro herramientas de código abierto más usadas para carga HTTP. La comparación se hace contra los requisitos de la sección 1; cada dato sale de la documentación oficial de la herramienta.

| | k6 | Artillery | JMeter | Locust |
|---|---|---|---|---|
| Scripts | JavaScript (ES modules) | YAML, con hooks en JavaScript | Planes XML, armados con una GUI | Python |
| Motor | Binario en Go, sin Node | Node.js | JVM | Python |
| Umbrales que hacen fallar la corrida | `thresholds` nativos | `ensure` | Por plugins o assertions | Por código propio (hooks de eventos) |
| Resumen exportable | `handleSummary` a JSON | Reporte JSON | Archivos JTL y reporte HTML | CSV y reporte HTML |
| Imagen oficial de Docker | Sí (`grafana/k6`) | Sí | No oficial | Sí |
| Documentación | [grafana.com/docs/k6](https://grafana.com/docs/k6/latest/) | [artillery.io/docs](https://www.artillery.io/docs) | [jmeter.apache.org](https://jmeter.apache.org/usermanual/) | [docs.locust.io](https://docs.locust.io/) |

## 4. Matriz de decisión

**Pesos.** Suman 100 y reflejan qué pesa más para este equipo:

| Criterio | Peso | Por qué |
|---|---|---|
| Lenguaje de los scripts | 30 | El requisito 6: el equipo escribe JavaScript y TypeScript, y un script que no se entiende no se mantiene |
| Umbrales que hacen fallar la corrida | 25 | El requisito 3: sin esto la prueba no corta en CI y hay que leer los números a mano |
| Integración con GitHub Actions | 20 | El requisito 5: el pipeline del proyecto vive en Actions (`.github/workflows/`) |
| Resumen exportable | 15 | El requisito 4: el artifact es la evidencia del TP |
| Requisitos del runner | 10 | Menos dependencias, menos que fijar y actualizar |

**Puntajes.** Escala de 0 a 2, con un criterio que se puede comprobar en la documentación de la sección 2: 2 = lo trae nativo, 1 = se logra con plugins o código propio, 0 = no lo trae.

| Criterio (peso) | k6 | Artillery | JMeter | Locust |
|---|---|---|---|---|
| Lenguaje de los scripts (30) | 2 (JavaScript) | 1 (YAML más JavaScript) | 0 (XML y GUI) | 0 (Python) |
| Umbrales (25) | 2 (`thresholds`) | 2 (`ensure`) | 1 (plugins) | 1 (código propio) |
| Integración con Actions (20) | 2 (imagen oficial) | 2 (imagen oficial) | 1 (imagen no oficial) | 2 (imagen oficial) |
| Resumen exportable (15) | 2 (JSON) | 2 (JSON) | 1 (JTL y HTML) | 1 (CSV y HTML) |
| Requisitos del runner (10) | 2 (un binario) | 1 (Node) | 0 (JVM) | 1 (Python) |
| **Total ponderado (sobre 200)** | **200** | **160** | **60** | **90** |

El total es la suma de peso × puntaje. **Elegida: k6.** Artillery queda segunda; la diferencia está en el lenguaje de los scripts y en que k6 no necesita Node en el runner.

Los puntajes son una valoración contra la documentación, no una medición. La prueba de concepto (sección 3) confirma o corrige la elección.

## 5. Despliegue incremental

Cada paso empieza solo si el anterior terminó en verde y alguien leyó el resumen.

| Paso | Script | Carga | Duración | Para qué |
|---|---|---|---|---|
| 1. Humo de carga | `humo.js` | 2 usuarios constantes | 1 min | Que los scripts, las guardas y los umbrales anden contra staging |
| 2. Stress | `stress.js` | Escalones de 10, 25 y 50 usuarios | 12 min | Encontrar dónde empieza a degradarse staging |
| 3. Soak | `soak.js` | 10 usuarios sostenidos | 33 min (2 de subida, 30 sostenidos, 1 de bajada) | Ver si se degrada con el tiempo: memoria, conexiones a la base |

Cada usuario repite una visita de un comensal anónimo: `GET /health`, `GET /api/discovery`, `GET /api/discovery/buscar?q=pizza` (cambiable con `K6_BUSQUEDA`) y, si Discovery trae restaurantes, `GET /api/discovery/restaurantes/:id` y `GET /api/menu/:id`. Entre requests hay pausas de 1 a 3 segundos (`scripts/carga/comun.js`).

### 5.1 Umbrales iniciales

Son **iniciales, a confirmar con la corrida de humo** antes del stress y el soak: no hay todavía una medición de staging que los respalde.

| Escenario | `http_req_failed` | p95 de `http_req_duration` | p95 de `/health` | Checks |
|---|---|---|---|---|
| Humo | < 1 % | < 800 ms | < 300 ms | > 99 % |
| Stress | < 5 % | < 1.500 ms | < 500 ms | > 99 % |
| Soak | < 1 % | < 800 ms | < 300 ms | > 99 % |

Por qué estos valores:

- **`/health` más estricto que el resto:** solo hace `SELECT 1` (`apps/backend/src/health/health.service.ts:53`), así que una demora ahí apunta a la base o a la red, no a la consulta.
- **Ningún p95 se acerca a los límites que ya existen:** 2 s del timeout de la base en `/health` (`health.service.ts:7`) y 10 s del smoke y de los scripts de carga (`scripts/smoke/lib.mjs:5`, `scripts/carga/comun.js`).
- **Stress más laxo:** busca el punto de quiebre, así que se espera ver degradación en el último escalón.
- **Corte temprano:** `http_req_failed` tiene `abortOnFail`. Si la tasa de error se dispara, k6 corta a los 30 s en vez de seguir cargando un staging caído.

Con el resultado del humo se ajustan los valores: `[PENDIENTE: corrida del dd/mm]`.

### 5.3 Cuándo no correr

- **Mientras alguien prueba staging a mano:** la carga le ensucia la prueba y los números.
- **Con Railway o Vercel con incidentes abiertos:** se mediría la caída, no la API.
- **Cerca del límite diario de Vercel:** el workflow no despliega nada, pero conviene no sumar ruido ese día.

### 5.4 Propuesta aparte: un flujo que escribe (sin implementar, necesita aprobación)

Un comensal que abre mesa y pide genera la carga real del servicio (sesiones, pedidos, Socket.io). Para probarlo haría falta:

- Crear antes, con el marcador `e2e-<run_id>`, una marca, un restaurante y mesas de prueba. Necesita un token de staff de staging.
- Abrir sesiones por QR, nunca por PIN: el PIN tiene un límite de 10 fallos por restaurante y bloquea 15 minutos (`apps/backend/src/sessions/sessions.service.ts:39`).
- Limpiar al final solo lo que lleva el marcador, igual que los e2e del backend.

No está en los scripts. Se implementa solo si se aprueba, en un PR propio.

## 6. Guardas

`scripts/carga/guardas.mjs` corre al cargar el script, antes de cualquier request. No imprime la URL ni el host: solo qué regla no se cumplió.

- `CONFIRMAR_STAGING` tiene que ser exactamente `si`.
- `BASE_URL` es la URL de la API, terminada en `/api`: `https://`, o `http://` solo en local (`localhost`, `127.0.0.1` o `host.docker.internal`).
- El host no puede ser de producción: ni `api`, `mesa`, `staff`, `admin` o `auth` de `menyu-app.com`, ni `menyu-backend-production.up.railway.app` (el dominio de Railway de la API de producción, que sigue activo: `docs/auth/VariablesACambiar.md:10`), ni los hosts de las variables `PROD_WEB_*_URL` del repo, que el workflow pasa en `PROD_HOSTS`.

En el workflow, `BASE_URL` sale de la `VITE_API_URL` de **preview** de web-cliente en Vercel, la misma que usa el smoke de staging en `deploy-staging.yml`. Nunca de la de production.

## 7. Comandos

### En local, con Docker (contra staging)

```bash
docker run --rm \
  -v "$PWD/scripts/carga:/carga:ro" -v "$PWD/resultados:/resultados" \
  -e CONFIRMAR_STAGING=si \
  -e BASE_URL='<URL de la API de staging, terminada en /api>' \
  -e K6_RESUMEN=/resultados/humo-resumen.json \
  grafana/k6:2.3.0 run --quiet /carga/humo.js
```

Cambiar `humo.js` por `stress.js` o `soak.js` según el paso. Con k6 instalado, lo mismo es `k6 run -e CONFIRMAR_STAGING=si -e BASE_URL=... scripts/carga/humo.js`.

### Contra el backend local

Con `pnpm --filter @menyu/api dev` corriendo en el puerto 3000, el `BASE_URL` es `http://host.docker.internal:3000/api` desde Docker, o `http://localhost:3000/api` con k6 instalado.

### Desde GitHub Actions

*Actions* → *Carga — k6 (staging)* → *Run workflow*: elegir el escenario y escribir `si` en *confirmar*. Desde la terminal:

```bash
gh workflow run carga-k6.yml -f escenario=humo -f confirmar=si
```

El resumen queda como artifact `k6-<escenario>-<run_id>`, guardado 30 días. Hay una sola prueba de carga a la vez (`concurrency: carga-k6`).

### Tests de las guardas

```bash
node --test scripts/carga/guardas.test.mjs
```

También corren en el CI, en el paso "Test — smoke scripts" de `ci.yml`.

## 8. Versión de k6

Fijada en `.github/workflows/carga-k6.yml` como `grafana/k6:2.3.0`, con su digest. Es la versión más alta publicada al 22/10/2026: la release v2.3.0 de `grafana/k6` es del 21/09/2026, y lo que salió después es v1.8.2 (12/10/2026), de la rama 1.x (`gh api repos/grafana/k6/releases`). El digest coincide con el de la etiqueta `2.3.0` en Docker Hub. Para actualizarla, cambiar la etiqueta y el digest juntos y repetir el humo de carga.

## 9. Deployments

- **Vercel:** el workflow no despliega nada. Solo lee la configuración de preview de web-cliente (`vercel pull`), igual que el smoke de staging.
- **Deploy — Staging:** `scripts/carga/**` y `.github/workflows/carga-k6.yml` están en el `paths-ignore` de `deploy-staging.yml`. Cambiar solo estos archivos no dispara un deploy.
